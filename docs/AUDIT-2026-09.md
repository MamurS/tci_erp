# TCI ERP — Whole-system audit, September 2026

**Scope.** Everything in the repository at commit `d140777` (Phase 6 merged), the
canonical Supabase project `reunqrpeumokqgarknge` (Postgres 17.6, region
`ap-northeast-1`), and the local Postgres 16 replay of migrations 0001–0042.
Read-only: no code, schema or test was changed. Every empirical probe against
canonical ran inside one transaction that was aborted at the end, and the row
counts were checked afterwards (4 entities, 0 relationships, 1 request,
1 decision, 2 users — unchanged).

**Method.** Catalog queries generated the RLS matrix, the SECURITY DEFINER grant
surface and the view-dependency graph; the claims those produced were then
tested with role impersonation (`set_config('role', …)` +
`request.jwt.claims`) as `anon` and as a throwaway user holding only the
`client` role and mapped to no policyholder. Money paths were read from the
last definition of each function in the chain. Scale numbers come from the
local harness with a synthetic 2,000-company / 3,000-edge registry.

Severity scale: **critical** = cross-tenant data or money can be changed, or
data can be lost; **high** = wrong money, wrong coverage, or the system stops
working at realistic size; **medium** = should fix before real operations;
**low** = hygiene. Effort: XS < ½ day, S ≤ 2 days, M ≤ 1 week, L > 1 week.

**Recommended first three phases** (detail in `docs/UPGRADE-ROADMAP.md`):
1. **Security closure** — gate or revoke the ungated definer functions, replace

2. **Operational floor** — nightly logical backups with a restore drill,

   Postgres 17, paid tier or keep-alive for canonical.
3. **Scale and correctness of the group model + limit lifecycle** — materialised
   group membership, missing-rate safety, expiry as an explicit event.

## 1. Security & data isolation

### 1.1 Ungated SECURITY DEFINER functions reachable by any authenticated user — **critical**

**Evidence (catalog).** Of the 92 `SECURITY DEFINER` functions in `tci`
executable by `authenticated`, **51 contain no `has_role`/`is_staff` check**
and 33 of those still carry the default `PUBLIC` execute grant (the advisor's
`anon_security_definer_function_executable` warnings). The full gate scan is
reproducible with:

```sql
select p.proname, (p.prosrc ~* 'has_role|is_staff') as role_gate,
       (p.prosrc ~* 'my_client_entities|client_policy_guard|policyholder_users') as tenant_gate
  from pg_proc p join pg_namespace n on n.oid = p.pronamespace
 where n.nspname = 'tci' and p.prosecdef
   and has_function_privilege('authenticated', p.oid, 'execute');
```

**Evidence (empirical, rolled back).** As a user holding only `client` and
mapped to no policyholder, calling the functions with the real policy id from
canonical:

| call | result |
|---|---|
| `tci.file_overdue_notification(policy, buyer, today-100, 1000, 'UZS')` | `{"result":"filed", "reported_late":true, "suspension_decision_id":"e047…"}` — an NOA was filed on a stranger's policy **and the buyer's limit was revoked**; `limit_in_force_at` then returned `revoked … limits.systemReason.noaSuspension` |
| `tci.generate_premium_instalments(policy, replace => true)` | `12` — the stranger's premium schedule was regenerated |
| `tci.suspend_limit_for_claim(stranger's claim)` | returned a new decision id — a `revoked` decision written on the stranger's buyer |
| `tci.open_task('submission_declined', 'legal_entity', …, 'sales', …, 'urgent')` | 1 forged urgent task visible to the sales department |
| `tci.emit_workflow_event('request.bound', …)` | 1 forged event, which fires the three Agenda mapping triggers as owner |
| `tci.verify_claim_coverage(stranger's claim)`, `tci.close_tasks(…)` | ran without refusal |
| `tci.policy_liability_consumed / policy_afl_consumed (policy)` | returned figures (0 here, because canonical has no claims) |
| `tci.buyer_has_effective_limit(policy, buyer)` | `true` — discloses another policyholder's limit position |
| `tci.limit_in_force_at(policy, buyer, today)` | the full decision row incl. `system_reason_key` |
| `tci.submit_declaration`, `tci.correct_declaration` (stranger's declaration) | refused only by **content** checks ("no lines", "only accepted … can be corrected"); neither has a permission or tenant gate |

The `anon` role cannot reach any of this — but only because `anon` has no
`USAGE` on schema `tci` (verified: 85 relations and 9 functions all refused
with `42501 permission denied for schema tci`). That is a single wall; the
functions themselves carry no defence.

**Why it matters.** The portal will be opened to real policyholders. Any
policyholder login can then revoke competitors' limits, create claims-side
side effects, spam the underwriting Agenda and read exposure positions on
policies it does not hold. This directly contradicts CLAUDE.md ("the database
is what enforces") and the Phase 3d claim that every client write goes through
a `client_*` function — the `client_*` functions are fine; it is the *internal
helpers next to them* that are open.

**Root cause.** Helpers written to be called from other SQL functions
(`open_task`, `close_tasks`, `emit_workflow_event`, `suspend_limit_for_*`,
`generate_premium_instalments`, the `policy_*_consumed` readers) were granted
to `authenticated` because their SECURITY INVOKER callers
(`decide_limit_request`, `advance_insurance_request`, …) execute as the
caller and need the grant. The grant is therefore load-bearing and cannot
simply be revoked.

**Fix shape (M).** Two options, both contract-testable: (a) add an explicit
gate to every internal helper (`is_staff()` where staff-only; for helpers a
`client_*` entry point legitimately reaches, an internal-call flag set by the
trusted caller via `set_config('tci.internal_call', …, true)` and checked by
the helper); or (b) convert the invoker-mode workflow functions to definer
mode with their own gates and revoke helpers from `authenticated`. Either way,
add a test that reads the catalog and fails on any `SECURITY DEFINER` function
executable by `authenticated` whose body has no gate and is not on an
explicit allow-list — the same pattern 0042 used for `anon`.

### 1.2 RLS matrix — generated, and empirically sound for base tables

45 tables in `tci`, **all** with RLS enabled, 118 policies. Not one policy
predicate mentions `client`; base-table client policies were dropped in 0025 as
documented. Empirically the unmapped client user could `select` from all 85
relations without a permission error and saw rows only in `countries` (249),
`currencies` (12), `industries` (21) and `user_roles` (1, its own). Staff
tables split into `[staff]` read + `[has_role]` write as CLAUDE.md describes.
Three reference tables are `[OPEN]` to every authenticated user by design.

**Preserve this.** It is the reason finding 1.1 is confined to functions.

### 1.3 The security_invoker nesting rule — complied with, but the catalog misleads

`pg_depend` lists five `v_client_*` views as depending on invoker views
(`v_effective_limits`, `v_declaration_lines`, `v_declaration_totals`,
`v_overdue_notifications`, `v_policy_premium`). Their definitions show they
read through the `client_*()` SECURITY DEFINER functions of 0030 (the
dependency is on the function's `setof <view>` return type). The rule holds,
but a catalog check alone would report a violation — keep the empirical check
in the smoke, and add it to CI (§8).

### 1.4 `P0004` as the permission error code — **high**

81 `raise exception … using errcode = 'P0004'` across the chain. `P0004` is
`assert_failure`, which PL/pgSQL's `WHEN OTHERS` deliberately does **not**
catch. Observed during this audit: two probes wrapped in `exception when
others` aborted the whole block on a permission refusal. Any future SQL
wrapper, batch job, or pg_cron task that catches errors will misbehave, and
PostgREST maps it as a generic 400 rather than 403. Use `42501`
(`insufficient_privilege`) for permission refusals and `P0001` for rule
refusals; the frontend maps by message fragment, so no UI change is needed.
`to_uzs` likewise raises `P0003` (`too_many_rows`) for a missing rate.

### 1.5 Forced password rotation is client-side only — **medium**

`tci.user_profiles.must_change_password` appears in no policy, view predicate
or function guard (0 references outside the column and its column grant). The
gate lives in `src/auth/passwordGate`. A provisioned user with the temporary
password can call the REST API directly without ever rotating. Add the
predicate to `is_staff()`/`has_role()` or to the portal views, or drop the
claim that rotation is "forced".

### 1.6 Storage, provisioning, secrets — sound

* `claim-documents` is private; four `storage.objects` policies derive the
  claim id from the path and gate on `may_access_claim` / `may_upload_to_claim`
  (`authenticated` only). Good.
* The provisioning service checks the caller's token and loads roles
  server-side; hardening middleware (1 MB body, 30 s timeout, anchored CORS
  regex, per-IP + per-caller buckets, opaque 500s with request id, non-root
  container) is present in `services/analytics/app/hardening.py` and covered
  by 25 tests. It is **not hosted**, so none of it protects anything today.
* No secret in tracked files; `.env.example` files carry names only; the
  service-role key is read only in `supabase_admin.py`.
* **Repository hygiene (low):** the repo carries three unrelated projects
  (`Fineye`, `Fineye_api`, `Fineye_dim` — 136 tracked files, referenced by
  TCI only in comments), a `CREDIT REPORT SAMPLE` directory and a directory of
  screenshots at the root. They widen the secret-scanning and CI surface and
  will confuse anyone rebuilding from the repo.

### 1.7 Supabase advisors

`security`: 23 `security_definer_view` errors (all the `v_client_*` views and
the two admin views — by design, but the two admin views are also flagged
`auth_users_exposed` and deserve a column review), 91 authenticated-definer
warnings (see 1.1), 33 anon-definer warnings (mitigated by the schema grant;
close them anyway), `set_updated_at` has a mutable search_path, **leaked
password protection is off** and **MFA options are insufficient** for an
insurer's staff accounts.

## 2. Correctness of money paths

Every monetary function was read at its last definition. Rounding is
consistent — `round(x, 2)` at every step of `calculate_indemnity` (0037) and
`record_recovery` (0034); 143 columns are `numeric(18,2)`; no floats.

### 2.1 fx conversion — time of evaluation

`tci.to_uzs` → `tci.latest_uzs_rate` always takes the latest rate on or before
**today** (`rate_date <= current_date`). Authority checks, `v_buyer_exposure`,
`v_group_exposure` and group-limit enforcement therefore move with the rate
every day. For *controls* this is defensible and documented. Two consequences
to state plainly: (a) a group limit set in UZS against USD member limits can
be breached by a currency move with no decision being taken — nothing raises
an Agenda task for that; (b) `credit_assessments` store the engine limit in
the statement currency, and the authority comparison at decision time uses
that day's rate, so the same decision can be inside authority one day and
escalated the next. **Low**, but it belongs in the underwriting manual.

### 2.2 Missing fx rate breaks the group screen — **medium**, contradicts CLAUDE.md

CLAUDE.md (Phase 6 rules): "Rows without a rate are counted separately, never
treated as zero." Verified on the local harness with an EUR limit and no EUR
rate: `v_buyer_exposure` → `(null, missing_rates=1)` ✔; `v_group_exposure` →
`(0, missing_rates=1)` ✔ — but only because the aggregate's `FILTER` clause
short-circuits `to_uzs`; **`select … from tci.v_group_exposure_lines`** (what
`GroupExposurePanel`, `GroupMembersTable` and the report section read) raises
`no UZS rate for EUR`. `group_exposure_preflight` also raises for a new amount
in a rate-less currency, which is consistent with the personal-authority path
(0023 line 198) and acceptable. Fix: compute `amount_uzs` in the lines view
with `latest_uzs_rate` and a null check, as `v_buyer_exposure` does. XS.

### 2.3 Premium — correct

`premium_instalment_count` measures `age(expiry + 1, inception)`: a
1 Jan–31 Dec policy yields 12 monthly / 4 quarterly instalments (the 11-month
bug the smoke caught is fixed and asserted in 0027). `generate_premium_instalments`
rounds each instalment to 2 dp and gives the remainder to the last one, so the
schedule sums to the minimum exactly. `v_policy_premium.adjustment_amount =
greatest(earned − minimum, 0)`; `premium_due_total` respects `premium_basis`.
Rate is frozen per entry (`rate_used`). One gap: `premium_entries` is written
on acceptance; on a *correction* that supersedes an accepted declaration the
audit could not confirm the original entry is reversed — verify with a test.

### 2.4 Limit validity — silent expiry — **high** (also §10.1)

`v_effective_limits` (0023) filters `valid_until is null or valid_until >=
current_date`. A limit with a `valid_until` simply disappears from every
screen at midnight; `decision_lifecycle.expired` is **never written**
(0 occurrences; 0013 line 541 calls it "reserved"); no `workflow_events` row,
no client notice, no Agenda task other than `limit_review_due` 30 days
earlier. `limit_in_force_at` (0033 line 81) respects `valid_until` at the
shipment date, so coverage verdicts are right — the operational cliff is that
the policyholder is not told.

### 2.5 Point-in-time coverage depends on a mutable setting — **low**

`decision_effective_from` (0033 line 44) computes a silent-consent release as
`decided_at + make_interval(hours => tci.sales_window_hours())` — the
*current* setting. Changing `workflow_settings.sales_window_hours` rewrites the
history of when past decisions reached the policyholder and can flip a
coverage verdict on a claim. Stamp `released_at` when silent consent occurs
(a lazy pass exists already) or store the window on the decision.

### 2.6 Indemnity, recovery, DL split, NOA timeline — correct

* Indemnity order (covered debt → NQL threshold `>=` → insured % → each-loss
  deductible → remaining AFL → remaining max liability) matches Allianz Trade
  practice and is asserted on source text and in TypeScript.
* Recovery: costs off the top; insurer share `round(net × ins_borne /
  total_borne, 2)` capped at net; policyholder takes the remainder, so shares
  add back exactly.
* `classify_declaration_line`: with a limit the whole turnover is covered;
  without one, cover stops at the DL and the excess is separate.
* `noa_deadline = first_due + max_extension + noa_window`;
  `claim_eligible_from = min(due) + waiting_period`, `null` for insolvency
  (callers must handle null — they do).

### 2.7 Engine rounding parity — documented, untested

`credit_engine.limits.round_limit` uses Python's banker's rounding
(`round(2500/1000) = 2` → 2000); SQL `round()` is half-away-from-zero. The
figure crosses the boundary once (`credit_assessments.suggested_limit`) and is
then a stored fact, so there is no live divergence — but nothing tests it, and
a future SQL re-derivation would silently differ.

## 3. Schema & migrations

### 3.1 Ledger drift between the repository and canonical — **critical** (with 9.1)

Canonical's `supabase_migrations.schema_migrations` lists **17 entries with no
file in the repo** (`agenda_buyer_added_event`, `agenda_bound_completes_accepted_task`,
`agenda_handler_verbatim_from_0024`, `agenda_limit_held_carries_request_id`,
`agenda_buyer_needs_entity_carries_request_number`,
`bind_stops_writing_rendered_notes`, `bind_insurance_request_verbatim_from_0023`,
`realign_0024_functions_verbatim_with_files`, `client_portal_proposals_and_views`,
`client_portal_actions`, `client_portal_policies_machine_agenda`,
`client_portal_contact_details_and_profile_grant`, `client_buyer_proposals_grant`,
`0026_declarations_body_sync`, `0027_premium_fix_freeze_update`,
`0027_premium_fix_instalment_count`, `0026_declarations_fix_correction_order`),
and two repo files (`0025_client_portal.sql`, `0042_…`) were applied under
different names or in pieces. The *resulting schema* is believed equal (the
repo versions were "realigned verbatim"), but nothing proves it: no schema
diff has been taken between a fresh replay and canonical. `supabase db push`
from the repo would try to re-apply 0025–0042.

### 3.2 Churn and stacked replacements — **medium**

`decide_limit_request` is defined 7 times, `v_effective_limits` and
`v_buyer_exposure` 7 times each, `refresh_agenda` 4 times (each a verbatim
carry-forward of ~350 lines with new sections appended), 33 `drop` statements,
133 `security definer` declarations. In-migration assertions check
*substrings* of the carried-forward bodies, not equality with the previous
version. A consolidated baseline is warranted for fresh environments:

* **What:** one `0000_baseline.sql` generated by `pg_dump --schema-only` of a
  clean replay, plus the reference-data seeds (countries, currencies,
  industries, UZ NAS templates), plus a `tests/db/` suite carrying every
  in-migration assertion as an executable test. The 42 files stay in history.
* **Cost:** ~3 days (dump, strip owner/grants noise, port 42 assertion blocks,
  prove `baseline ≡ chain` with a schema diff on PG17, wire into CI).
* **Risk:** losing the *narrative* in the migration headers — keep them as
  `docs/schema-history.md`.

### 3.3 Index coverage — **medium**

71 single-column foreign keys have no index. Most are `created_by`-type
columns that are never filtered on. The ones on real query paths:
`policyholder_users.user_id` (evaluated by `my_client_entities()` on **every**
portal read), `credit_limit_decisions.adjusts_decision_id` and
`based_on_assessment_id`, `overdue_notifications.entity_id`,
`declarations.supersedes_id`, `entity_relationship_suggestions.entity_b`,
`tasks.source_event_id`, `legal_entities.industry_id`. S.

### 3.4 Triggers and columns — **low**

Nine tables have `updated_at` without the `set_updated_at` trigger (`claims`,
`claim_invoices`, `declarations`, `declaration_lines`, `entity_relationships`,
`entity_relationship_suggestions`, `overdue_notifications`,
`premium_instalments`, `workflow_settings`); some functions set it by hand,
others do not. `set_updated_at` has no pinned `search_path`. Dead enum value
`decision_lifecycle.expired`. Policy names are inconsistent with table names
(`"limit_decisions: …"` on `credit_limit_decisions`).

### 3.5 Environment parity — **medium**

Canonical runs **Postgres 17.6**; the local harness runs **16**. The
`pg_trgm`-in-`extensions` and `auth.uid()` stubs live only in the session
scratchpad (`bootstrap.sql`, `replay.sh`) — CLAUDE.md documents the harness
but the repo does not contain it.

## 4. Workflow engine

### 4.1 Group resolution scalability — **high**

Local harness, PG16, 2,000 companies, 3,000 live edges (400 parents × 4
children + 1,400 cross-holdings):

| query | time |
|---|---|
| `select * from tci.v_entity_group where entity_id = X` | **637 ms** |
| `select * from tci.v_group_financials where ultimate_parent_id = X` | **72,841 ms** |
| `tci.refresh_entity_suggestions(X)` | 9 ms |
| `tci.refresh_agenda()` (no limits/policies) | 93 ms |

`v_entity_group` evaluates `tci.ultimate_parent(e.id)` twice and a `count(*)`
sub-select per member row, each a fresh recursive walk. `v_group_financials`
selects `distinct ultimate_parent_id, member_id from v_entity_group` for the
**whole registry** before the filter can apply, because the filter is on a
function result. `v_group_exposure_lines` calls `ultimate_parent` once per
effective limit. At a realistic 5,000-company registry the Группа tab is
unusable and the decision-form preflight (which reads `v_group_exposure`)
degrades with the number of in-force limits.

Fix: a `tci.entity_group_members (ultimate_parent_id, member_id, depth)` table
maintained by a trigger on `entity_relationships` (recompute the affected
component only), with the views reading it; keep `entity_group()` as the
recomputation primitive and the cycle fixture as its test. M.

### 4.2 Lazy generation on read — **medium**

`refresh_agenda` scans policies, instalments, NOAs, effective limits, groups
and tasks on every Agenda open (`staleTime` ≈ 1 min per staff user). It is
idempotent through `tasks_open_uq` + `on conflict do nothing`, and a retire
pass runs after each open pass, so two concurrent calls cannot duplicate but
can briefly flap a task closed→open. Cost grows linearly with portfolio size
and is paid by the reader. Supabase provides `pg_cron`; CLAUDE.md's "no cron
anywhere" was a phase-scoping choice, not a constraint. Recommend a
5-minute `pg_cron` job under an advisory lock, with the on-read call kept as a
cheap "refresh if last run > 60 s ago" gate.

### 4.3 Concurrency — mostly sound

`decide_limit_request` locks the request `for update`; a second underwriter
deciding an `escalated` request sees `decided` after the lock and is refused.
Double submission is prevented by `credit_limit_requests_open_uq` (partial
unique on the coalesced scope key). `overdue_notifications_open_uq`,
`claims_live_uq`, `declarations_live_period_uq`, `group_limits_live_uq` cover
the other one-open-object rules. Weak spot: `suspend_limit_for_noa` and
`suspend_limit_for_claim` supersede the effective decision without locking it;
two simultaneous suspensions both write a `revoked` row (harmless, but the
chain then has two effective→superseded transitions). Low.

### 4.4 Lingering tasks — **medium**

Ten of eleven original task types close on events; events are emitted only by
the SQL functions. A status changed by any other path (a raw PATCH through a
still-permitted RLS policy — `claims: staff update` allows it — or an admin
fixing data in the SQL editor) leaves the task open forever; there is no
reconciliation sweep and no admin view of stale tasks. The forged-event
finding (1.1) is the same surface from the other direction.

## 5. Frontend architecture

### 5.1 Bundle — **high**

`dist/assets/index-*.js` = **1,933,060 bytes** (549 KB gzip), one chunk, 48
routes, **0** `React.lazy`. `recharts` (2 import sites) and `xlsx` (1 site,
`lib/exportTable.ts`) are in the main bundle, so a policyholder opening the
portal on a phone downloads the whole underwriting workstation including the
spreadsheet exporter. Route-level lazy loading per feature folder and
`manualChunks` for the two libraries is a day's work and roughly halves the
first load.

### 5.2 Data fetching — **medium**

`supabase/config.toml` sets `max_rows = 1000`; the app has **59** list queries
of the form `.select('*')` with no `.range()`/`.limit()` (3 in total). The
registry, the Agenda, the claims queue and every history list will silently
truncate at 1,000 rows. `QueryClient` defaults are sensible (`retry: 1`,
`refetchOnWindowFocus: false`). The Supabase client uses default session
persistence (localStorage) — acceptable for staff, worth a review for the
portal.

### 5.3 Error handling — **medium**, contradicts CLAUDE.md

Only `claims/errors.ts` and `groups/errors.ts` map database refusals to
messages (both contract-tested against migration text). Elsewhere: 20 bare
`catch {` vs 8 `catch (e)`; `t('common.saveFailed')` 10×, `requests.*Failed`,
`limits.proposals.failed` — the limits, requests, policies, declarations and
portal features turn deliberate refusals ("request is escalated and cannot be
decided", "exceeds your authority") into "could not save". There is **no
ErrorBoundary** (0 occurrences): a render error blanks the page. Generalise
the claims pattern into one `lib/sqlErrors.ts` registry keyed by SQLSTATE and
fragment, contract-tested once against the whole chain.

### 5.4 Pure-module + contract-test pattern — strong, with gaps

44 test files, 548 cases, 3.2 s. 25 files import migration text (`?raw`),
locking 24 migrations. Every feature folder has at least one test. Gaps:
`api.ts` hooks (0 tests), components (0), no test touches a database, and the
declarations/overdue/portal modules are thin. The ratio engine exists twice —
`features/entities/financials/ratios.ts` (147 lines) and
`credit_engine/ratios.py` (173 lines) — with no parity test.

### 5.5 Accessibility and mobile — **medium**

No `eslint-plugin-jsx-a11y`. 21 `aria-` attributes and 63 `role=` across
35,000 lines. `Modal` handles Escape and sets `aria-modal`, but has no focus
trap and does not return focus. One `autoFocus` in the app. Dynamics colours
are paired with ▲/▼ glyphs (good). 51 responsive-prefix uses in total
(`sm:` 21, `md:` 8, `lg:` 16, `xl:` 6); the portal shares the desktop shell and
`Table` overflows horizontally on narrow screens. The portal is usable on a
tablet and not on a phone.

### 5.6 Formatter discipline — **low**

DESIGN.md: "`src/lib/format.ts` is the only formatter". Three violations, all

## 6. Design system & UX

* DESIGN.md is 67 lines and still points at
  `src/features/buyers/financials/lines.ts`, which moved to `entities/` in
  Phase 3a — docs drift (XS).
* Empty states: `EmptyState` used in 42 feature files; the protocol's "every
  screen has a designed empty state" is largely met.
* Navigation: 12 sidebar items filtered by role, 48 routes, up to 9 tabs on a
  company card. Reasonable for the six roles; the portal has its own shell.
* i18n: 1,722 keys in en and uz, 1,726 in ru — the four extra are `_few/_many`
  plural forms (`buyers.overview.exposurePolicies`, `limits.missingRates`)
  that uz lacks, so uz renders the singular for every count. 178 dynamic keys

  enum-coverage test that walks every `*_TYPES`/`*_STATUSES` constant.
* No raw server strings reach the UI; the leak is the opposite — deliberate
  refusals are hidden behind generic messages (5.3).

## 7. Analytics service & engine

* **Placement.** The deterministic engine is 536 lines of table-driven scoring
  (`scoring/tables.py`: 15 `ScoreTable`s, `BASE_WEIGHTS`, `GRADE_BANDS`) plus a
  benchmark limit model (`limits.py`: working-capital and trade components,
  halved). CLAUDE.md's rounding argument against a TypeScript port stands. The
  Python service is the right home; **it must be hosted** — today rating,
  fx and provisioning are all dead in production and the screens sit in their
  "unavailable" state. Cloudflare Containers ($5/mo) or Render Starter ($7/mo)
  are both prepared.
* **Contradiction with CLAUDE.md.** "Band families are served by the analytics
  service (`GET /grade-scale → family`), never hardcoded outside the band
  names" — yet `tci.grade_band_for_assessment` (0017) hardcodes
  `upper(left(rating_grade, 1))`. Authority routing therefore uses the first
  letter, not the service's family. Align (persist `family` on
  `credit_assessments` at write time) or amend the doc.
* **Calibration readiness.** Thresholds are "domain knowledge inherited from
  the legacy Fineye model"; no calibration dataset, no backtest, no
  score-distribution report exists in the repo. What the owner needs: a
  labelled corpus (statements + observed defaults/NOAs), a CLI that scores the
  corpus and prints grade distribution, AUC/KS and migration matrices, and a
  way to version the tables. M–L.
* **Undeclared dependency.** `narrative.py` imports the `anthropic` SDK and
  reads an API key; neither the key nor the SDK appears in
  `services/analytics/.env.example`, `pyproject.toml` or the README. Either
  declare and secure it, or remove the LLM path from the service image.
* Tests: 102 in `services/analytics`, 81 in `credit_engine`; CI builds and
  smokes the image.

## 9. Operations

### 9.1 Backups and disaster recovery — **critical**

There is no backup routine, no exported dump, no restore drill and no
statement of the plan's PITR status. The canonical project holds the owner's
real registry and statements. **Rebuild from the repo alone:** the *schema*
can be rebuilt (proved: 0001–0042 replayed on PG16 with a stub) but the
ledger will not match canonical (3.1), the stub is not in the repo, and the
*data* cannot be rebuilt at all. Minimum: a nightly GitHub Action running
`pg_dump` over the pooler with a repository secret, encrypted artifact
retention ≥ 30 days, and a quarterly restore into a Supabase branch with the
smoke suite run against it.

### 9.2 Tier, region, parity — **high**

Canonical is in `ap-northeast-1` (Tokyo) — ~150 ms from Tashkent on every
round-trip — on a plan that pauses after inactivity (the README's own
warning). Postgres 17 in canonical, 16 locally. No staging project; every
phase's smoke runs against production data inside aborted transactions, which
has worked but leaves no room for a mistake in a `raise`.

### 9.3 Secrets, observability — **medium**

Service-role key rotation is documented; anon-key rotation is not. There is no
frontend error reporting, no uptime check, no alert on migration failure; the
only structured log is the unhosted service's. User creation runs through a
SQL snippet in the dashboard with no audit trail of who ran it.

### 9.4 Migration procedure — **medium**

Migrations are applied by hand through the MCP `apply_migration` tool with
free-form names (the cause of 3.1). Use `supabase db push` from CI on merge to
`main`, against a branch first.

## 10. Domain fidelity (as a TCI practitioner would judge it)

### 10.1 Limit validity semantics — **high**

Market practice (Allianz Trade, Coface, Atradius): a credit limit is
**open-ended until withdrawn or reduced**, with a periodic review date; a
withdrawal takes effect from notice, and goods shipped before notice stay
covered. Here `valid_until` is a hard expiry that silently removes cover
(2.4). Recommend: treat `valid_until` as a *review date* that raises a task
and never withdraws cover by itself; withdrawal is always an explicit
decision with an event and a client notice.

### 10.2 Withdrawal and the order pipeline — **medium**

`limit_in_force_at` correctly judges cover at shipment, so a revocation is not
retroactive. Missing: the customary allowance for goods already ordered but
not yet shipped at the date of withdrawal, and the policyholder-facing notice
with its date — today the client sees the revoked row appear.

### 10.3 Discretionary limit conditions — **medium/low**

The DL is applied per buyer without recording the basis the policyholder used
(trading experience, credit report). Insurers condition DL cover on that basis
and dispute claims where it is absent. Capture it on the declaration line or
on a per-buyer DL justification.

### 10.4 NOA and claims timeline — **medium**

NOA deadline, waiting period and insolvency crystallisation are right. Missing:
a **stop-shipment** rule after the NOA deadline (shipments after the deadline
should be uncovered — today only the notification-duty breach zeroes lines),
a **claim filing deadline** after the waiting period, and the **collection
mandate** (who collects during the waiting period) — Allianz makes collection a
policy service; here it is undefined.

### 10.5 What is missing for real operations — **high**

* **Endorsements**: policy terms are mutable columns; there is no effective-dated
  term history, so a mid-term rate or DL change silently rewrites the past.
  The premium `rate_used` freeze protects premium but not coverage or claims.
* **Renewals**: no renewal flow, no expiry pipeline, no rollover of limits.
* **Reinsurance / treaty cession**: no capacity, no cession per policy/buyer/
  country, no XoL attachment — every limit decision is judged against
  authority only, not against retained capacity.
* **Country limits and policyholder-group exposure** (the mirror of Phase 6).
* **Regulator reporting** (Uzbek supervisor forms) and **audit-trail export**:
  history is immutable in the tables but there is no export.
* **Premium regimes**: deposit premium, rate per country/grade, premium tax.

### 10.6 What is faithful — preserve

Two-stage decisions with a commercial stage bounded to amount and terms; the
authority band matrix; emergency reductions bypassing the sales window; the
DL/uncovered-excess asymmetry with freezing on acceptance; the NQL as a
threshold with equal-qualifies; the indemnity order; pro-rata recovery
distribution; point-in-time coverage from decision history; group exposure
netting off the superseded scope.

## What is genuinely good and should be preserved

1. **RLS on every table with no client policy on any base table**, and the
   client surface confined to `SECURITY DEFINER` views and `client_*`
   functions — empirically a stranger with a portal login sees reference data
   and nothing else. Finding 1.1 is an exception to this design, not a flaw
   in it.
2. **Business logic in SQL with assertions in the migration itself** (cyclic
   fixture in 0038, NQL boundary in 0037, `text[]` cast in 0035, "no client
   view reaches the group surface" in 0040).
3. **The contract-test pattern**: 25 test files lock TypeScript mirrors to
   migration text; it has caught real drift and should be the model for the
   error-mapping and enum-coverage tests proposed here.
4. **Immutability where money moved**: decisions superseded, never updated;
   frozen indemnity trace; frozen declaration split; `rate_used` on premium
   entries; override columns that never overwrite the system verdict.
5. **Point-in-time coverage** reconstructed from decision history rather than
   current state.
6. **The Agenda as generated, self-retiring tasks** with i18n keys instead of
   rendered text in the database.
7. **The analytics service hardening** — already at the level a public
   endpoint needs; it only needs hosting.
8. **i18n discipline**: parity test, uz terminology guard, glossary in
   CLAUDE.md, no hardcoded UI strings found.
9. **CI that fails on the real checks** (`tsc -b`, not `--noEmit`) and smokes
   the container.
10. **CLAUDE.md as an engineering record** — the "rules that are easy to get
    wrong" sections are the most valuable documentation in the repo; this
    audit found three places where it is now wrong (1.1, 2.2, 7) and they
    should be corrected there, not just here.
