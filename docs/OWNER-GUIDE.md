## 1. Supabase: вход и защита учётных записей

Дашборд: <https://supabase.com/dashboard/project/reunqrpeumokqgarknge>.

### 1.1 Включить шлюз входа

Сейчас вход без «билета» с формы входа разрешён и только записывается в
журнал. После включения такой вход блокирует учётную запись до разблокировки
администратором. Так закрывается подбор пароля в обход формы и её счётчика
попыток.

1. Убедитесь, что новая страница входа (с обратным отсчётом после неудачных
   попыток) уже в продакшене. Она уже в `main`. Попросите всех, кто работает
   в системе, один раз обновить страницу (Ctrl+F5).
2. В приложении: **Администрирование → Безопасность**, блок «Контроль входа ещё
   не включён» → **Включить**.
3. Если кого-то заблокировало: там же, в списке блокировок, **Разблокировать**.
   После разблокировки система сама потребует сменить пароль.

Выключается той же кнопкой.

### 1.2 CAPTCHA (Cloudflare Turnstile)

**Порядок важен.** Сначала сайт должен уметь показывать CAPTCHA, и только
потом Supabase начинает её требовать. Иначе вход перестанет работать у всех.

1. **Cloudflare → Turnstile → Add widget.**
   - Hostnames: `tci-erp.pages.dev` (и свой домен, если подключён).
   - Widget mode: *Managed*.
   - Сохраните **Site key** и **Secret key**.
2. **Cloudflare → Workers & Pages → `tci-erp` → Settings → Variables and Secrets
   → Add**.
   - Тип *Text*, имя `VITE_TURNSTILE_SITE_KEY`, значение — Site key.
   - Добавить отдельно для **Production** и для **Preview**.
3. **Deployments → последний production-деплой → Retry deployment.** Переменная
   попадает в сайт только при сборке. Откройте страницу входа и убедитесь, что
   под формой есть виджет Turnstile и что вход проходит.
4. **Supabase → Authentication → Attack Protection** (в некоторых версиях
   *Bot and Abuse Protection*):
   - **Enable CAPTCHA protection**;
   - Provider: **Turnstile**;
   - Secret key — из шага 1;
   - **Save**.
5. Проверьте вход ещё раз.

Политика безопасности сайта (CSP) уже разрешает Turnstile, менять её не нужно.

### 1.3 Двухфакторная защита (MFA)

Защиту проверяет сама база: без второго фактора администратор после
включения не получит доступа ни к чему, даже в обход интерфейса.

1. **Supabase → Authentication → Multi-Factor**: убедитесь, что **TOTP**
   включён. Обычно включён по умолчанию.
2. В приложении: **Аккаунт** (меню учётной записи) → **Двухфакторная
   аутентификация → Включить**.
   Отсканируйте QR-код приложением-аутентификатором (Google Authenticator,
   1Password, Authy) и введите код.
3. Сохраните резервный доступ: в 1Password или Bitwarden QR-код хранится
   вместе с паролем. Потеря телефона без резервной копии означает разблокировку
   через SQL.
4. Напишите мне — я включу обязательность MFA для администратора и, если
   хотите, назначу дату, с которой она станет обязательной для остальных
   сотрудников. Для клиентов MFA остаётся по желанию.

### 1.4 Утёкшие пароли и лимиты частоты

- **Authentication → Providers → Email → Prevent use of leaked passwords**
  включить. Если переключатель недоступен на вашем тарифе, пропустите.
- **Authentication → Rate Limits**: уменьшите лимит входов (*sign-in /
  token verifications*) по IP. Мой ориентир — несколько десятков попыток за
  5 минут. Ваших пользователей это не заденет, а подбор пароля замедлит.
  Точное значение решаете вы.
- **Хук Password Verification** не нужен. Он есть только на тарифе Teams,
  и его работу на вашем тарифе выполняет хук Custom Access Token, который уже
  включён. Поэтому подсказка на экране «Безопасность» о хуке проверки пароля
  на тарифе Free неактуальна.

## 2. Бэкапы

Каждую ночь в 02:17 по Ташкенту GitHub делает дамп базы, шифрует его вашим
ключом и хранит 30 дней. Расшифровать дамп может только владелец закрытого
ключа. Полная инструкция с восстановлением — [`docs/BACKUP-RESTORE.md`](BACKUP-RESTORE.md).

Что сделать вам (≈ 15 минут):

1. **Ключ на своём компьютере**, не на сервере:
   ```sh
   age-keygen -o tci-backup.key      # macOS: brew install age; Ubuntu: sudo apt install age
   ```
   - Файл `tci-backup.key` — **закрытый ключ**. Храните его офлайн (флешка
     в сейфе плюс копия в менеджере паролей). Без него ни один бэкап не
     восстановить.
   - Строка `age1…` — **открытый ключ**, он не секретный.
2. **Строка подключения**: Supabase → **Connect** → **Session pooler** →
   скопировать URI, подставить пароль базы, дописать `?sslmode=require`.
3. **GitHub → репозиторий → Settings → Secrets and variables → Actions → New
   repository secret**, два раза:
   | Имя | Значение |
   |---|---|
   | `SUPABASE_DB_URL` | строка из шага 2 |
   | `BACKUP_AGE_RECIPIENT` | открытый ключ `age1…` |
4. После слияния PR #39 в `main`: **Actions → Nightly backup → Run workflow**.
   Запуск должен быть зелёным, и в нём должен появиться артефакт `tci-…`.
5. **Пробное восстановление** (раз в квартал, первый раз — сразу). Скачайте
   артефакт, расшифруйте своим ключом и восстановите в локальный Postgres по
   разделу 3 [`BACKUP-RESTORE.md`](BACKUP-RESTORE.md). Это проверяет, что ключ
   и бэкап действительно работают. Могу пройти его с вами по шагам.

## 3. Хостинг сервиса аналитики

Сервис считает рейтинги и рекомендуемые лимиты, ищет компании в реестрах и
создаёт пользователей. Пока он нигде не запущен:

- пользователей создаёт только SQL из [`docs/create-user.sql`](create-user.sql);
- **клиентский портал нельзя открывать реальным страхователям**.

План — Cloudflare Containers на вашем аккаунте Cloudflare, $5 в месяц (тариф
Workers Paid). Пошагово, с таблицами значений:
[`services/analytics/README.md` → Cloudflare Containers → Owner steps](../services/analytics/README.md#owner-steps).
Коротко:

1. Workers & Pages → Plans → **Workers Paid**.
2. **Create application → GitHub** → этот репозиторий:
   - имя `tci-analytics`;
   - ветка `main`;
   - Deploy command `npx wrangler deploy`;
   - Root directory `deploy/cloudflare-analytics`.
3. В настройках сборки отключите Preview Builds и задайте Build watch paths.
4. **Секрет `SUPABASE_SERVICE_ROLE_KEY`**: Supabase → Project Settings → API
   keys → `service_role`. Он даёт полный доступ к базе: только сюда, никуда
   больше.
5. Проверка: `<адрес>/health` и `<адрес>/users/provisioning-status`.
6. В Pages-проекте `tci-erp` переменная `VITE_ANALYTICS_API_URL` = адрес
   сервиса, затем Retry deployment.
7. **Пришлите мне адрес** — я добавлю его в CSP (`connect-src`). Без этого
   браузер не пустит запросы к сервису.
